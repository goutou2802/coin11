### 7.2 ⛔ 最大的坑：任务面板一旦真正滚动，无障碍树当场失效

这是本次最重要的负面结论，实现必须绕开：

| 实验 | 结果 |
|---|---|
| 首次进入面板，立刻 dump | **正常**：426 nodes / 174 条宝内文本 / 8 条计数 |
| 大滑 `swipe(720,2500,720,1150,0.35)` | 内容滚到底（截图证实），dump 掉到 **81 nodes / 宝内文本 6 条 / 计数 0** |
| 慢拖 `swipe(720,2400,720,1600,1.2)` | 同样死：174 → **23 条文本 / 计数 0** |
| 小步挪 `swipe(720,2300,720,2110,0.6)` ×8 | 树**一直活着**（8 行计数在），但**内容一步都没动**（行 y 完全不变）→ 小位移根本没触发滚动 |
| 死后 `d.reset_uiautomator()` | **无效**（仍 80 nodes / 6 条文本），耗时 2.4s |
| 死后干等 12s 轮询 dump | **无效**，始终 81 nodes |
| 死后 `d.press("back")` 回淘金币主页再进 | **无效**，整页树都是死的 |
| 死后 `am force-stop` + `am start` + 重走导航链 | **有效，树恢复**（426 nodes） |

结论与要求：

1. **判定"滚动是否真的发生"不能看有没有发 swipe，要看行的 y 有没有变**——小位移会被吞掉，
   只是"看起来滑了"（本次 8 次 190px 位移全部无效）。
2. **只要滚动生效，树必死**，且只能靠 force-stop + 重走导航链恢复（约 10–15s）。
   → **首屏能解决的事，绝不要滚动**；需要底部行时，优先接受"首屏 + 截图人工核对"，
   或为滚动单独付一次冷启动成本。
3. 因此"遍历全部 11 个任务"在手机1 上**不适合用滚动实现**；
   更稳的做法：一次冷启动 → 只读首屏 → 做完首屏可做的 → 冷启动换批。

## 10. 给实现环节的硬结论

1. 面板元素 `resource-id` 全为空，定位只能 `text` 全等／正则 + `bounds` 几何校验。
   建议同时校验 `x1==308`（任务名列）或 `x1==1136`（按钮列），避免误命中下层页面的广告文案。
2. **行有重名**：`买限时折扣好物得奖励(0/1)` 在首屏出现 **2 次**（#2、#6，bounds 不同）。
   所以"按文本定位"必须返回**列表**，用 `bounds.y` 或序号消歧，不能取第一个就算。
3. **首屏与滚动后的行序会变**，坐标不可跨屏复用；每次点击前重新 dump。
4. **不要滚动**（§7.2）；要做底部任务就单付一次冷启动。
5. `完成进度 20/20` 与 Activity 名都不能当判据；判据只能用**行内 (n/m) 推进或整行消失**。
