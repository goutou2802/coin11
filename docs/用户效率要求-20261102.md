# 用户提出的效率优化要求（2026-11-02）

> 来源：用户在使用过程中逐条提出。**这些是需求，不是建议**。
> 实施时必须逐条对照，并在代码里注明「2026-11-02 用户要求」。

## 1. 打开淘宝后不要做"主页面判断"，直接进淘金币页
用户原话："主页面也没必要判断，我看昨天晚上那些都是打开淘宝直接进淘金币页面，很流畅"

- 现状：ensure_taobao_home() 会 OCR 找「我的淘宝/领淘金币/搜索/购物车」四个锚点之一，找不到就 force-stop 重开，最多 2 次。
- 要求：**跳过这道判断**，am start 后直接按已知路径点进去（首页「领淘金币」图标 (159,938)，规则 intent=coin_entry 已存在）。
- 保留 force-stop 只作为**兜底**（点完还是不在面板时才用），不要作为启动必经步骤。

## 2. 浏览时长在"扫描"时就解析好，不要进去再判断
用户原话："滑动时间的判断可以直接放在扫描里，不要进去再判断"

- 现状：parse_rows 已能从副标题解析 secs（如「浏览15秒」→15），但进去后仍有一段"先看计时走不走再决定滑不滑"的逻辑（已默认关闭，但代码还在）。
- 要求：**扫描阶段就把每行的 secs 定下来**，进去后**直接用**，不做任何二次判断。

## 3. 相似任务的时长可以直接复用
用户原话："很多任务是相似的，例如有 0/5 这种轮次的浏览时间都是一样的，这样点击进去就直接滑动"

- 观察：同一批 (n/m) 的浏览任务，副标题秒数通常一致（如都是「浏览15秒」）。
- 要求：维护 secs_cache，按「行形态 + 名称族」记住上次秒数；同族任务再次执行时**直接用缓存**，跳过重新解析。

## 4. 扫描策略改成"一页一页做"（最重要）
用户原话："任务扫描可以先扫一页，把一页的任务做完，并且刷新的也做完，再滑动去找有没有在下面或者底部，在上面看不见的任务"

- 现状：drive_panel 仍是"选一行→做→再选"的逐行模式，且入场可能全表扫描。
- 要求：
  1) **只扫当前可见这一页**，得到这一页的可做行清单；
  2) **把这一页所有可做行依次做完**（做完一行的行会被新任务顶替，**新顶替上来的也要做**）；
  3) 这一页再没有可做行时，**才向下滚动一屏**，重复步骤 1；
  4) 滚到底（连续两屏内容一致）→ 该面板收工。
- 收益：省掉每轮"回顶部/重新导航/全表扫描"的开销；新刷新出来的任务能立刻被吃掉。

## 5. 总原则
- **能不做判断就不做**：点进去 → 滑满规定秒数 → 返回 → 下一个。
- **所有"确认型"动作都有代价**：每多一次截图/OCR ≈ 1.5~3 秒，一天几十轮就是几十分钟。
- 判断只在**真正不确定**时做（连续失败、面板丢失），不是每轮都做。
## 6. 【最高优先】点进去到开始滑动之间有 5~10 秒浪费（2026-11-02 用户实测）
用户原话："为什么还不是点进去直接滑动，还是要截图识别，滑动有很长时间延迟，不用滑动的任务奖励都到账了才开始滑动"

**代码位置**：`coin11/auto.py` `one_round()` 第 2888~2932 行。
当前顺序（每项都有代价）：
  tap(2888) → sleep 1.4s(2889) → grab 截图+OCR(2892, 约3~5s) → handle_jump_dialog(2897, 可能再 grab)
  → landing_after 复核落地(2909, 可能多次读屏) → browse_dwell(2924/2931, 内部还要先截一张 before)

**要求改成的顺序**（对普通浏览类任务）：
  tap → sleep 1.5s → **直接 browse_dwell 滑满 secs** → back → 一次复核
  即：**不做落地截图、不做跳转框检查、不做落地复核**。

只在以下情况才走进阶判断：
  - `card["kind"] == "search"`（搜一搜，必须先提交关键词再浏览）
  - 连续 2 轮失败（说明确实落错地方了）

**验收标准**：一个「浏览15秒」任务，从 tap 到开始滑动的间隔 **≤ 2 秒**（现在 5~10 秒）。

## 7. 监控面板「最近轮次」不更新（2026-11-02 用户反馈）
用户原话："那个监控最近轮次怎么不更新"

- 排查方向：dash.py 读的可能是固定目录/固定日期，或轮询缓存未失效；
  也可能两个 auto.py 实例写不同 run 目录，面板只读其中一个。
- 要求：面板每次轮询都重新扫描 `evidence/*-auto/rounds/` 下**最新**目录，并显示数据来源路径与最后更新时间。

## 8. 出现"滑动任务→识别半天→返回→去滑任务列表"的错乱（2026-11-02 用户反馈）
用户原话："刚刚还出现了滑动任务截图识别半天还返回再滑动任务列表的"

- 症状：本应在商品页滑动，却回到了面板并在**任务列表上滑动**。
- 可能原因：落地判定失败 → 提前返回；或 SWIPE_DOWN 坐标在面板页上执行。
- 要求：**滑动前必须确认当前不在面板上**（面板有标题+行尾按钮），在面板上绝不执行浏览滑动；
  同样，返回后如果发现还在面板上，说明这一轮根本没落地，应记为 `skipped` 而不是继续滑。
## 9. 点击后等待时间：0.2 秒（2026-11-02 用户要求）
用户原话："为什么要等1.5秒啊，等0.2秒得了"
- 代码位置：`one_round()` 里 `dev.tap()` 之后的 `time.sleep(...)`，已从 1.4 改为 **0.2**。
- 理由：页面没加载完时滑动是无害的空滑，早滑比晚滑好；等待纯属浪费。
- 如果 0.2 秒导致落地判定经常失败，可回调到 0.5，但不要回到 1.4。
## 10. 服务必须"脱离会话"启动，否则会随会话结束一起消失（2026-11-02）

现象：teach.py（8777/8778）和 dash.py（8899）如果用 agent 的 run_code 后台任务启动，
**会话结束或任务被清理时会一起被杀**（退出码 2304），用户看到的就是"教学页打不开"。

正确做法（任选其一）：
- 让用户双击 `coin11/run.bat`（它会启动面板 + 跑任务）；
- 或启动时用脱离父进程的方式：Windows 下 `subprocess.Popen([...], creationflags=0x00000008)`（DETACHED_PROCESS），
  或用 `start "" /b python ...` 从独立 cmd 窗口起。

另外：**手机2 的无线调试地址会变**（IP 和端口都可能变，如 192.168.1.4:5555 → 192.168.1.5:43059）。
连不上时先问用户当前的「IP:端口」，不要反复重试旧地址。
